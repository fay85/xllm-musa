# 原生启动问题与加载顺序

独立 C++ 进程首次引入 DeepEP Python ABI 时，Python/C++ 创建的 musa:0 Tensor 都带了 CUDA dispatch key，随后 fill_ 报 CUDA backend 未实现。仅修改头文件顺序、改用生产 mcc 编译器、预加载 backend_init 都没有解决。v1/v2 八 rank 都自行 exit -6，故障发生在测试数据创建阶段，还未执行 LL；显存均已释放，没有 SIGKILL。

单卡最小对照显示：使用同一 mcc 编译的 probe，只将 LD_PRELOAD 改为先 libmusa_python.so、后 libmusa_backend_init.so 后，Tensor 的 key_set 成为 PrivateUse1，Python 创建/C++ 填充和原生创建/C++ 填充均通过，exit0。该方式也与仓库 tools/musa_unified/deepseek/run.py 的初始化顺序一致。它是进程动态库加载顺序，不修改驱动或系统安装。不能把这个小检查当成完整 DeepEP/模型成功。

完整候选源码已 CPU 编译成功（e43_native_full_v1，exit0、0 errors）；H64 Sparse AOT 也已完成。真实权重头部预算：E42 TP8参数60.278798GiB，owner target/draft TP8参数66.369433GiB，增加6.090635GiB；对照E42实际69.387695GiB，预估75.478330GiB，尚需量化LL buffer/Graph/加载峰值，不能直接据此宣布80GiB可装下。
