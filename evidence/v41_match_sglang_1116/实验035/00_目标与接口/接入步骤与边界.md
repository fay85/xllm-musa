# E35：真正DP8/DeepEP的可行接口验证

当前控制基线为E34（0db84ab5、31.51346ms/30.21984token/s）。本项先验证实际可用的通信接口，不提前修改模型并行或替换累计最佳。

新证据：从冻结SG镜像提取其实际DeepEP动态库，SHA090e0fe2…，310408272字节，存于NFS `dependencies/deepep_sg_b_090e0fe2`。不是镜像附带的旧rc43 wheel。提取用未启动的runc/no-network临时容器，按CID核验后已删除。

在我方现有Torch2.9.1、torch_musa2.9.1+a18d871的容器中，显式隐藏所有GPU、隔离PYTHONPATH导入deep_ep_cpp/deep_ep成功，GPU runtime未初始化。实际pybind Buffer方法签名见api_result.json。**这只证明库可装载，不证明通信/Graph/数值正确。** 无需因缺少公开C++头文件就停止研究，可考虑C++在初始化/捕获阶段调用已存在的pybind接口；模型forward仍原生C++，数据不搬到CPU算。

下一步顺序：
1. 阅读现有SG低延迟路径的环境和缓冲合同；CPU获取容量提示与pybind签名，核对SDK、mtshmem、NIC及实际SO。不要调用旧xLLM同名但不同ABI的DeepEP类冒充兼容。
2. 空闲现场复核后，独立8rank最小dispatch→已知专家函数→combine：真实hidden5120、target384专家/top6、draft128专家/top3；q1/q4/q6、只有一个DP rank有token/其他空rank、-1路由、跨token重复访问专家、非均匀路由权重；比较显式参考。先同步路径，再非默认stream和静态Graph输入变化回放。缓冲必须遵守最多两组未回收结果的限制，保存所有进程身份/失败日志；设备异常停止强制操作。
3. GPU通信通过后，C++窄桥接采用相同生产入口/对象生命周期，先单算例验证Torch Tensor零拷贝和当前流，不要求重写整个通信库。Graph捕获前建立buffer，捕获阶段不能初始化分布式组或分配通信池；回放不能依赖Python host动作。
4. 再接MATE masked S4FP8、mask有效行和原权重scale；明确combine是否已带路由权重和归约，避免重复相加。最后才做D端DP token归属、Attention/H64所有者、空rank、共享专家、LM-head及P/D缓存适配。

若隔离桥接不支持Graph或ABI在真实Tensor调用中失败，保留证据，选择匹配源码/依赖隔离或其他有证据target融合路线；不强行覆盖已验证模型环境，不以导入成功声称DP8接入完成。

初始记录为CPU前置验证。后续已推进GPU算例，最新结论见本实验的兼容性记录；仍不能视作已完成模型DP8接入或性能提升。
