# E38：DeepEP LL 与真实 MATE 专家计算完成短检查

我已把 DeepEP 的专家接收布局接到原生 C++ W4A8 专家计算入口。target 第0层的384个专家、MTP第0层的128个专家，使用原 W4AFP8-mt1017 的真实权重，完成8卡通信、计算及动态Graph检查。**这是后续 owner/DP 执行的前置实现，尚未接入完整模型，不替换累计最佳，不宣称端到端提速。**

仅通过基础功能检查，未完成模型精度验收。

## 为什么做、参考什么

冻结的SGLang B以DeepEP low_latency分发token，接收expert-major BF16数据和有效行数，量化后调用两次MATE S4FP8 GEMM，再按原rank及路由权重合并。参考文件在 `01_参考依据/SG_真正DP8与DeepEP_LL` 的 `deepep.py`、`musa_w4a8_moe.py`、`musa_w4a8_ll_prep.py`，版本及SHA沿用E35冻结证据。

我方E37仍在每个rank上处理复制的token，再归约局部专家结果。E35只验证过通信和已知缩放函数，不能证明真实专家GEMM、量化和缓存布局能够衔接。本次补上这一缺口。

## 改动在什么位置

- `xllm/core/kernels/musa/deepseek_v41_w4a8.cu/.h`：新增 `deepseek_v41_w4a8_quant_dispatched`，直接量化已分发的有效BF16行。保留expert/slot顺序；counts为0时不读未初始化padding；支持当前动态group128及权重静态scale。
- `xllm/core/layers/musa/deepseek_v41/w4a8_experts.h`：新增 `forward_dispatched`，复用生产MATE gate/up GEMM、SwiGLU量化、down GEMM。输出未乘路由权重的BF16专家矩阵，交回DeepEP combine。原 `forward` 路径保持本地分发、FP32局部加权输出。
- 测试模块直接组合既有C++ `DeepseekV41DeepEpLlBridge` 与生产专家类。Python仅启动和验证；专家数学在MUSA GPU上执行。Gloo在capture外汇总小型参考输出，未将模型计算回退到CPU。

路由权重仅在combine应用一次；该结果之后不能再做原来的routed EP all-reduce。共享专家仍需在完整owner/DP接线时明确归约，这次没有伪称已验证共享专家接入。

## 检查结果

每rank102项，共816项：6项带NaN padding的独立量化Graph检查；target/MTP各动态与静态scale、q1/4/6，覆盖owner0/3/7、负路由、其他rank真0行、全空、全active，以及改变输入/路由/owner的回放。

有效行量化与独立GPU参考逐值一致。各专家收到的token数精确一致；新链路与当前GPU专家计算加独立归约比较，最大relative RMS为 **0.0005220767（约0.05221%）**，沿用2%门限，没有为了通过放宽门限。权重来自所有rank不同的真实专家切片，并非复制两个专家构造假负载。

检查8rank和局部测速8rank均正常exit0，未发送TERM或SIGKILL。06:27两机GPU均空闲核验完成，之后才启动E39。

## 遇到的问题及修正

1. v1独立CUDA编译漏了MusaMapping环境，错误识别CUDA兼容头；按E36成功构建的环境重编。模块v2成功，SHA `58cedf1c2c2a488609d327368338ee0e5c69d4e7e93a818b78bdee36faf9bd07`。
2. GPU v1缺少明确的TileLang库路径，FFI加载检查失败，8rank自行abort；补齐本容器用户态库路径。未修改宿主驱动。
3. GPU v2的动态target检查已通过，但静态scale路径需要Apertoken导出，E36库只导出了Apergroup。按相同SG修正头、编译选项、MATE0.2.6隔离编译静态库；SHA `9a23ce3a6dfe2381e20573ae17643fba3d22760a79dd1e390bb5ab4531a36241`。v3完整通过。两次失败原始日志均保留。
4. 校正此前E35文字：当前E37模型实际用动态group128，不能笼统写成“模型已有静态scale”。SG使用权重静态scale，新增独立E39整模型对照验证其效果，不把依赖更新、DeepEP与量化变化混成一个收益。
