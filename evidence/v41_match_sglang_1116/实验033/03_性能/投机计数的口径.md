# 验证接受计数不等于最终交付的接受 token 数

本次请求最终交付长度由客户端usage、EvalScope数据库和服务端generated_tokens三者核对为256。`speculative_accepted_tokens`统计的是验证结果中的接受个数；`DFlashWorkerImpl::record_validate_metrics`在worker输出上计算，`Batch`在逐token append及finished/max_tokens检查前累计。最后一个block可以含达到长度上限后未实际交付的token。因此不能用 accepted + 验证轮数 + Prefill首token 当作已交付256的恒等式，也不能把该accepted计数直接称为“实际输出的草稿token数”。

代码证据：`xllm/core/runtime/dflash_worker_impl.cpp::record_validate_metrics`、`speculative_worker_impl.cpp::calculate_contiguous_speculative_token_stats`；`xllm/core/framework/batch/batch.cpp`中先调用record_speculative_token_stats再append_token_for_sequence，序列finished后停止追加。

本轮固定每轮proposal3，无自适应缩短：提出330/333对应110/111轮验证工作量。这是执行成本对照；最终吞吐分子仍严格采用实际交付256，而非验证接受数或提案数。每个最终交付token的总体工作量可用轮数/256、proposal数/256表示。未额外记录逐token来源，所以不虚构最终交付的draft/target细分。

冻结SGLang B日志的accept len/rate是周期窗口统计，也不与我方请求末尾计数直接等同。它只能提示不能先验认定SG是靠更高接受率变快。
