# 本轮之后的优化顺序与需要补的证据

本轮按用户要求完成G01/G02并推进至T14，不以每个开关都打开为成功标准。后续应从本轮已接受的同负载配置继续，不重置到最初eager慢基线。以下是本轮结束后的新工作，不代表已做完，也不把SOL待确认写成达标。

1. **先缩小P端同步/退出可靠性问题。** E57仅移除progress日志后长输入RPC超时，E40当前流fence并未完全消除时序边界。用最小P端collective与实际流依赖诊断；记录各rank就绪和错误首因，不靠加入日志/反复SIGKILL“修复”同步。该问题直接关系长请求稳定性，优先于再堆性能开关。出现D态/设备异常停强制操作。
2. **真实batch的Attention与metadata还可摊薄。** 本轮将mHC/Dense/MoE批量化，但Attention保留逐请求cache与状态，q增大不代表所有成本线性摊薄。下一轮应对最大实际q的代表步，测各rank等待与独占GPU忙区，优先融合独立请求的页表/索引/压缩缓存处理，再测同C2/C4两组，保持每条256输出。不能用总kernel数直接预测收益比例。
3. **MTP先提高有效工作比，再尝试速度。** 当前接受率约20～23%，有target回放和完整快照开销。先明确接受prefix可提交的ratio2/Engram/辅助hidden状态，使target的30输入行尽量减少；不能直接删除恢复/重放。随后独立测试proposal1/2/3，区分draft、verify、state维护与接受行，低接受率下主动记录失败策略。不要宣称“接入draft就是提速”。
4. **Graph重新选择捕获边界和通信策略。** 现有FFN尾Graph实际慢，不启用。先用单层、真实权重、可观测Graph内部GPU节点的对照确认串行等待来源，再决定捕获Attention/FFN还是只固定输入。Graph与已有mHC/cache fusion收益有重叠，不把它们分别的理想收益相加。
5. **后续才是CED/新并行布局。** CED需要独立精度/跨层状态合同；其他TP/EP/DP/CP需解决当前80GiB容量和native限制。当前TP4EP8的80.454GiB必要静态量已超过单卡容量，须先降低Engram/冗余权重常驻或调整专家布局，不能直接改几个数字承诺能跑。新增服务器需要新的资源授权。
6. **SOL口径和完整精度另立验收。** 请领导确认实际硬件峰值/带宽、模型FLOPs/bytes与服务口径；H200实测只作不同实现参考。之后按阶段补完整模型精度、数值偏差与官方语义回归。用户本轮明确暂不做MathQA/API/logits，报告始终标注“仅通过基础功能检查，未完成模型精度验收”。

每项仍保存目的→参考源码→固定before→相关短小正确性→官方两组5次正式→同条件trace→局部与全局收益→接受/拒绝。局部可移除占比未知时写unknown，先测清楚再排优先级；不要用重profiler的CPU嵌套区间相加，填出漂亮但不可核验的百分比。
