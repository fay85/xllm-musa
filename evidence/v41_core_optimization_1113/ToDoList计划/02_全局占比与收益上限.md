# 从全局 trace 到可兑现的收益上限

## 1. 本次真正重新分析了什么

只对已有 StageI 本地 raw trace 做离线统计：SJ10 rank0 最后 3 个 decode step，kv=261/262/263；SJ9 rank0 一个 256-token prefill step。统计记录、源文件 SHA、脚本在 [依据/当前Trace占比](依据/当前Trace占比) 与 [工具](工具)。没有新跑推理，也没有把离线分析写成新的实测优化。

CPU 端按最深层 `V41/` 语义区间分配独占 wall time，排除父子重复计数；GPU 用 runtime correlation 关联 kernel。该关联只覆盖模型主线程发出的可关联操作，**不能把 `EP_allreduce` 行的 0 个关联 kernel 解释为没有通信**。MCCL 可能由其他线程/图发出，需另看全部 GPU 轨道。

| D rank0 捕获步 | CPU step 窗口 ms | 窗口内 GPU kernel 区间并集 ms | MCCL 区间并集 ms | 其他 kernel 区间并集 ms | 无 kernel 区间 ms |
|---|---:|---:|---:|---:|---:|
| kv261 | 501.078 | 342.250 | 290.306 | 51.944 | 158.828 |
| kv262 | 503.467 | 334.588 | 282.315 | 52.273 | 168.879 |
| kv263 | 493.662 | 382.548 | 332.348 | 50.200 | 111.114 |

这里以 **CPU step 窗口裁剪**，GPU 异步执行可能跨窗口；不是已经同步 drain 的完整 GPU step。三窗中 MCCL 与其他 kernel 的区间未观察到重叠，不代表其他运行方式也无重叠。MCCL 的驻留时间包含潜在的慢 rank 等待；无 kernel 区间也可能由 profiler、CPU 调度、同步、未覆盖 activity 造成，不能直接叫“可消除的 CPU 开销”。

## 2. 当前已有一个可严格限定的全局上限

在并发 1、固定生成 256 token、保持后续 decode 不变的条件下，假设把**整个 TTFT**降为零：

| 工作负载 | 当前端到端 | TTFT | 全部 TTFT 占比 | 端到端时间最多减少 | 输出吞吐最多提高 |
|---|---:|---:|---:|---:|---:|
| 256/256 | 46.0315s | 0.36027s | 0.7827% | 0.7827% | 0.7888% |
| 2048/256 | 48.5258s | 2.44458s | 5.0377% | 5.0377% | 5.3049% |

实际 Prefill GEMM、P/D 传输、tokenizer 各自只是 TTFT 的一部分，上限还要更低。这是**当前 C1 端到端输出速度**优先查 decode 的依据；不是说 TTFT 不重要。当目标改为 TTFT SLA、长输入或高并发时，优先级必须重排。

## 3. 后续如何得到能排序的 p

固定 case、版本、并行、缓存及采样，分三层计时：

1. 客户端：请求开始、首个真实内容 token、每个 token、结束；保留实际 token IDs、流式事件、服务器 usage。首个 HTTP 字节不一定是首 token。
2. 服务端：排队/组批、P forward、P/D 状态准备与 transfer、D 首步/稳态步、采样/序列化。请求 ID 与 step ID 贯穿，跨机器绝对时间需记录时钟误差，优先使用本机单调时钟的持续时间。
3. 设备及各 rank：低开销 MUSA event 或 runtime 原生 timer，记录 stream 的 start/end，并在采集窗口末批量读取；不要每个 kernel 后强制 synchronize。统计各 rank 到达 collective 的偏差、输入字节数、dtype、实际后端、等待消费者及独占关键路径。

先用 profiler OFF 与轻量计时 ON 比较开销；预注册 3% 为可接受目标，超出则降低抽样频率，不能机械扣除一个常数。详细 C++ stack/ATen trace 另采小窗口，只做归因。通信微基准可做 ready 同步后的算法比较，但其同步会去掉真实 rank 偏差，不能拿它取代服务结果。

`p` 是**可以被该改动缩短、且没有被其他工作遮住的关键路径时间 / 相同 case 的总时间**。一段 kernel 持续 10ms 若完全被别的工作遮住，可移除关键路径可能接近零。MCCL 等待慢 rank 的时间与慢 rank 的 CPU 工作不能各算一次再相加。

记录 `p_low/p_high`、统计范围、关键路径/重叠证据。若只有 profiler scope 或 kernel duration sum，标 `proxy`；如果完全没测，标 `unknown`。G02 完成后，同一个目标 case 内按 `p_high` 降序排可比较任务；相同上限时，以证据更强、数值风险更低、开发代价更小者先做。两个任务覆盖同一时间段时作为候选替代，先完成一个后重新测另一项剩余上限。

## 4. 上限与兑现率公式

局部速度变为 r 倍、可缩短关键路径占比为 p：

`T_new / T_old = (1-p) + p/r`

`端到端加速比 S = 1 / [(1-p)+p/r]`

`时间降幅 = p×(1-1/r)`；假设该部分可完全消除，`S_max=1/(1-p)`。

例如 p=20%、局部快 2 倍，整体时间只降 10%、速度快 11.11%。这是教学示例，不是本模型的测量。TPOT 与 E2E 分别计算；固定输出 N 时用 `E2E≈TTFT+(N-1)×TPOT` 作核对，并解释最终流结束等差异。

每项实验先冻结 `T_ideal` 及假设，优化后计算：

`上限兑现率 = (T_before - T_after) / (T_before - T_ideal)`。

不使用“速度百分比 / 时间百分比”，不使用 kernel 次数下降率代替性能兑现率。上限未知则兑现率 `N/A`；若超过 100%，说明上限估算漏项、环境/精度/工作负载变化或测量误差，需要复核，不能直接宣称突破理论上限。若没有完全兑现，区分残余计算、重叠改变、同步、额外访存、启动开销、rank 不均衡及噪声，逐项给证据。
