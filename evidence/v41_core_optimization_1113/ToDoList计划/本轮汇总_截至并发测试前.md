# 本轮累计优化：结果、证据和边界

本文对应SJ9/SJ10、W4AFP8-mt 1017、原生C++模型路径。模型为`/data/nfs_shared/models/DeepSeek-V4.1-Flash-1017-W4AFP8-mt`，不是原版FP4/group32。当前固定P/D各8卡，Attention/共享专家TP8，路由专家EP8，DP1/CP1。GMI实际显示X10000 80GiB；未用未经确认的S5000宣传指标计算SOL。

**仅通过基础功能检查，未完成模型精度验收。** 领导要求优先推理速度，模型只检查两道算术题；保留修改相关的算子、通信、缓存短小回归。文本/数值差异记入实验，未做MathQA、API或固定前缀一致性验收。本轮没有证明完整官方语义和所有缓存/投机组合等价。

## 先看单请求结果

初始G01同环境复测：256/256为TTFT314.05ms、TPOT179.49ms、端到端46.0844s、输出5.5550token/s；2048/256为2354.05ms、180.99ms、48.5058s、5.2777token/s。

累计接受TP/EP小消息custom all-reduce、缓存对象复用、SWA读取融合、共享专家TP切片、Decode当前模型stream与mHC尾归约融合后，E38两组TPOT为67.15/66.19ms，输出14.6130/13.0940token/s。这是累计顺序中的实测值，单项收益不能相加。

E47进一步只将Prefill chunk256改512，长输入2048/256的TTFT2693.98→1510.82ms（降低43.92%），端到端19.8769→18.6741s，输出12.8793→13.7088token/s。短输入没有收益，因此短输入继续用已测chunk256；不能把分开验证的两个参数设置说成同一轮统一profile。

E28是重复Prompt场景：长输入正式5条均实际命中1792个prefix token，TTFT345.40ms、TPOT66.30ms、输出14.8382token/s。它是热前缀负载的收益，不能替代冷请求成绩。

## 为什么这些改动可能有效、图上如何看到

mHC：同一层的prepare保留MATE投影，把后续归约/缩放/rsqrt组合为我方MUSA融合kernel。8个Decode rank均核对到80个融合调用/step，完整trace减少400个GPU kernel/step；真实ATen sum/div/rsqrt等消失，mm349保持。对应独立正式测速TPOT降低10.51%/13.13%。详见E38图文报告。

Chunk512：同一2048token冷请求，每个Prefill rank从8个q256变4个q512；P0完整trace kernel约59976→29972，Decode仍为q1。更少chunk可以减少重复模型调用与调度，也减少当前逐层诊断日志，因此不能把全部TTFT收益都归给GPU计算。详见E47。

Prefix：长请求保持2048实际输入，P仅算剩余q256，缓存命中1792。需要同时看请求usage、P终态cached-token日志、4q512→1q256的8rank trace；不能仅凭TTFT变小判定kernel本体变快。详见E28。

调用图使用实际进程ELF的PC回溯、实际RecordFunction ID与实际Kineto事件转换为Perfetto。火焰宽度为ENTRY_COUNT，**不是CPU耗时**。GPU时间线与关闭profiler的正式性能分开。未得到严格扣重的局部关键路径占比p，不能捏造Amdahl兑现率或60%SOL。

## 实验过但没有启用的路径

- Graph：三个模式实际正式测速，TPOT约74ms反而到127～128ms，关闭。捕获区的GPU子kernel可见性有缺口，不能用记录数减少证明工作消失。
- 共享专家packed、QKV合并、Gate缓存：真实ATen/GPU数量有减少，但正式收益小、两组取舍或重复置信不足，默认关闭。共享投影做了两轮各10条正式对照，没有只挑最好一轮。
- CED尾部SWA裁剪：长输入约1.86%端到端收益、短输入回退，完整语义尚未证明，不晋级。
- DSpark/MTP：已经实现原生draft模型、辅助状态、快照恢复/重放、P/D接入，修复drafter缓存512/576维度识别。两道算术、两组正式、10次长请求稳定性、前后全部32rank trace通过；实际接受率约20～23%，验证与回放使D target输入行7→30、总kernel24787→50941，TPOT66～67ms→172～174ms，关闭spec。它是功能闭环的负收益结果，不是高速MTP已完成。移除逐层日志后的单独控制试验出现长输入RPC超时，因此未继续把该配置用于DSpark，也未篡改原有数据。
- TP/EP替代布局：完成实际权重头、加载切片和容量计算。TP4EP8仅必要常驻量约80.454GiB已超过80GiB，尚未含KV/scratch；当前没有做成功的TP4/DP/CP性能实验。不把容量判断说成所有其他并行方式都不可行。
- P/D搬运：已有非零transfer region约2.003ms均值，但尚不清楚ready/wait与关键路径重叠；没有更换NIC/驱动，也不声称完成网络优化。

## 实现和依赖需要怎样表述

模型主体、缓存和通信编排走C++，自写MUSA kernel负责已实测的融合/索引/缓存等；Python用于构建、客户端、离线核验与图表，不是让模型forward回CPU。专家使用转换资产的signedINT4/group128权重与实际MATE W4A8算子；不能称为原版E2M1/group32已高速接入。

两端镜像为`registry.mthreads.com/presale/devtech/xllm:1102-dev`，imageID09b8f5f4…；实际pip元数据为torch2.9.1、torch_musa2.9.1、mate0.2.7、mate-mubin0.2.7、TVM-FFI0.1.11.post1+musa.1。模型显式加载另行冻结的W4A8/sparse/mHC SO：W4A8 SHA6757da6f…、sparse212fbdd1…，不以pip名称猜测具体预编译算子的修订版本。源码构建可参考`build_w4a8_mate.py`，其中保留交付SGLang的修正头与编译选项；已进一步核对`04_数值验证/w4a8_mate_v2_build.json`：生成库SHA与运行库逐字节一致，构建时mate元数据同样0.2.7，实际导入源码为`/donor/mate`，修正头与JIT源码有独立SHA。该生成时记录的COMPILED_NOT_GPU_VALIDATED是历史构建阶段状态，后续GPU/模型验证见各实验；不能把这个字符串当作当前从未验证。不能自动声称运行的是最新MATE0.2.8。

## 稳定性与资源边界

E57删除逐层日志后，短输入成功但长正式0/5、P rank0 RPC超时退出；剩余7rank正常TERM无效，按持续授权重新核验身份后各一次SIGKILL，进程与GPU条目均释放。没有D态、GPU reset、驱动修改、Docker服务重启、主机重启或BMC操作。不能把progress日志视为同步问题的根治。
