# 如何阅读本轮两组性能

当前先准备解释，真实结果只在测试完成后填写。本轮部署为P(TP8)+D(TP8)、BF16 eager、并发1；输入/输出256/256与2048/256，各1次预热加5次正式请求。全部真实输出包含思考token，性能测试用ignore_eos保持目标长度，不能拿这个开关下的正文做MathQA评分。

| 指标 | 含义 | 不应混淆 |
|---|---|---|
| TTFT | 客户端发送请求至首个有效生成增量的延迟 | 包含服务入口、调度、Prefill等开销，不等于纯Prefill kernel时间；角色/usage空帧不应当作生成token |
| TPOT | 首token之后平均生成一个输出token的时间，常用(E2E−TTFT)/(输出token数−1) | 包含Decode相关通信、框架等待等，不只是GPU矩阵计算；终止帧/网络也可能带来小额差异 |
| E2E | 从请求发出到完成的整体延迟 | 不含模型启动时间；正式样本应与预热区分 |
| 请求吞吐/QPS | 正式测量窗口成功请求数除以窗口时间 | C=1的结果不能代表最大并发容量 |
| 输出吞吐 | 正式窗口输出token总数除以时间 | 与单请求decode阶段的1/TPOT不同，前者还受Prefill等时段影响 |
| 单请求decode输出速度 | (输出token数−1)/(E2E−TTFT) | 与全流程输出token数/E2E不是同一指标 |

输入token以模型chat template处理后的真实usage为准；输出token以服务端usage为准。若工具缺少usage而自行重新分词，需显式标记，不能无条件视为精确固定长度。报告保留5个正式样本，而非仅平均值；N=5不能作为可靠的p99服务等级承诺。

两组测试分别回答短输入和较长输入下的基线情况，不构成优化A/B。即使长输入TTFT升高，也不能据此量化其中KDA、DSA、MoE分别花了多少时间；模块级归因需要另有profiling证据。

EvalScope的报告可能包含名为trace的多轮请求分析数据，这不等于Moore Perf System的GPU kernel trace；不得把二者混称。
