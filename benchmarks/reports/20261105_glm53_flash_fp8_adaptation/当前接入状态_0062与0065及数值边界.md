# 当前接入状态、0062/0065与尚未解决的数值边界

本文件对应2026年11月5日的v14c实际运行配置。按用户最新要求，
保留问题记录，停止继续做分歧题复测和根因追查，转入两组性能测试，不抓新trace。
**“已接入”表示该实现实际参与了GPU推理，并有下述范围内的验证；不表示完整模型任意输入都已数值对齐。**

## 1. 0062到底改好了什么

原题是：

> today is thursday. i came home from a trip 3 days before the day after last monday. how many days have i been home?

选项为A=1天、B=2天、C=7天、D=6天、E=10天。官方初次选D。
按“经过整天”可算5天，含首尾日期可数6天，因此题目本身有计数口径歧义。
旧本地选B=2，不能用这项歧义解释2天。

本轮不是修改题目、提高思考力度或针对题号改答案。双方继续
temperature=0、top_p=1、reasoning_effort=low、max_tokens=4096。
采取并验证的改动有三个层次：

| 改动 | 遇到的问题与处理 | 证据及归因边界 |
|---|---|---|
| 保留mHC控制参数的原始FP32 | checkpoint的base/scale本来是FP32，但模型整体dtype转换后曾先以BF16接收，再升回FP32；现在在复制权重前恢复FP32目标参数 | 隔离v6使末层prefill相对HF误差从约18.58%降至10.63%，但0062仍没有答对；不能单独把修复归于这项 |
| TP归约显式使用FP32累加 | 原来各rank的BF16局部输出直接求和；当前先在GPU提升FP32，经MCCL求和，再转回BF16 | 同一实际投影的batch/single归约差异实验中，BF16求和有约0.0037～0.0048相对差异，FP32求和为0；单独采用这项的v9仍未答对0062 |
| KDA prefill选择MATE recurrent路径 | prefill原来用chunk算法、decode用recurrent算法；当前prefill逐token调用同一MATE递推内核，减少两种算法的算术顺序差异 | 34个实际KDA层、272个TP头切片的独立full/split输出及最终state差异为0；与HF数学参考仍有有限精度差异。代价是prefill并行度降低 |

组合后的v12：0062初次D、301个生成Token；额外3次均D、均301Token。
当前真实双机v14c：0062为D、301Token、正常stop，与官方初次选项一致。
**因此可以说“这道题在当前配置下的表现得到改善并复现”，不能说“已经证明唯一根因并彻底修复所有prefill/decode数值差异”。**
v11的另一种组合（Torch GPU FP32 KDA参考+FP32 TP）曾给E，已保留失败证据且未采用。

相关代码入口：

- xllm/python/models/glm5_next.py：mHC权重加载、_reduce_tp_output及其调用。
- xllm/python/kernels_musa/kda.py：recurrent_kda的显式prefill_mode。
- xllm/python/attention/musa_glm_reference.py：将模型配置传到KDA适配器。

## 2. 0065的“解决”应如何准确表述

该题问销售佣金：前100台每台售价10,000美元、佣金3%，其后4%，总佣金45,000美元。
精确计算为100+(45,000−30,000)/400=137.5台；选项没有137.5，原标签A=140。

旧BF16轮出现过4096Token耗尽、没有最终选项。本轮早期FP8 v4已经正常结束为A、
246Token；组合v12和当前双机v14c均为A、577Token、正常stop。
所以不能把0065的变化全部归因于后来新增的recurrent KDA/FP32归约，
也不能因为选A就声称数学事实完全正确。准确说法是：
**本轮该题没有重现旧轮预算耗尽现象，最终选项与官方初次和原标签一致。**

另有一次v8试跑被基础设施停滞中断，尚未取得完整响应；它与模型生成到4096的截断是两类事件，
日志分别记录，不合并为“模型答错”。官方同参数重复请求也曾在A/D等选项间变化，
说明temperature=0并不保证不透明的在线服务每次返回同一结果。

## 3. 相同token前缀却预测不同数字，具体发生在哪里

**它来自0062的专项teacher-forced诊断，不是新的一道题，也不是直接比较官方API与本地的最终A～E选项。**

先固定该题聊天模板后的116个Prompt Token，再固定一段19Token的思考前缀，
其文字末尾是“Thursday minus Saturday = ”。完整待比较前缀一共135Token。
诊断v13强制模型实际输入使用相同Token ID，避免两条生成分支已经写出不同文字却仍被误认为“同输入”。

两条路径分别是：

1. 先prefill原始116Token，然后逐个送入这19个固定Token，比较第135个输入之后的下一Token logits。
2. 把完全相同的135Token一次性prefill，比较同一位置的下一Token logits。

比较结果：

| 路径 | 下一Token top-1 | token ID | 该Token logit |
|---|---|---:|---:|
| 116Token prefill + 19Token逐步decode | 数字2 | 17 | 23.0 |
| 整段135Token prefill | 数字5 | 20 | 24.125 |

最后层hidden相对L2差异为0.275983，logits相对L2差异为0.229722。
两条路径的模型输入ID已核对完全一致。
诊断基于v12数学配置，使用单机native诊断实例，**不是双机P/D传输对比**；
所以不能把这项现象直接定性为网络传输、P/D缓存丢失或GPU通信死锁。
输出中被强制送入的文字也不能作为真实自由生成的答案去评分。

原始比较见日志/forced_v13_comparison.json，图见图/forced_prefix_v13.png，
诊断脚本为工具/prepare_forced_prefix_v13.py与工具/native_q62_forced_requests_v13.py。
大体积逐层张量保留在NFS的logs/diagnostic_forced_prefix_v13。

这是一项尚未解释清楚的**路径数值一致性风险**。它说明即使0062自由生成最终已经选D，
也不能宣称数值边界已经消失。可能涉及有限精度、矩阵形状、逐层误差放大、路由选择等，
当前证据未锁定唯一根因，不能给出“就是MATE某算子有bug”的结论。
独立HF参考在full/split间也有中间误差，但该位置两边仍预测5；
因此既不能要求所有浮点结果逐bit相同，也不能忽略已经改变top-1的差异。

当前对分的问题并不只有这一项：还有0076的真实算术错误、0088的正文数值与选项字母不一致，
以及若干题目标签/选项疑点。完整清单以本轮逐题CSV为准。按最新要求，本轮只记录，不继续追查。

## 4. 哪些已经接到MATE，具体怎样接

| 模块 | 当前实际路径 | 我方做的适配 | 已有证据与限制 |
|---|---|---|---|
| 路由专家 MegaMoE | **MATE FP8** fp8_fp8_mega_moe | 保留E4M3权重及FP32的128×128 scale；按EP8分配每卡36个完整专家；CPU离线重排字节布局后上传GPU；构造并复用IPC工作区；路由sigmoid/top8/归一化×2.5；保留clamp10；共享与路由归约分开 | 随机EP2/EP8、实际checkpoint层及实际激活形状实验、全模型逐层加载和双机推理；这不等于全模型所有数值问题消失 |
| KDA核心递推 | **MATE KDA**，当前prefill/decode均选择recurrent算法 | 对齐Q/K/V、raw gate/beta、A_log/dt_bias、FP32 state布局；接入框架状态槽读写；保持safe gate及归一化语义 | 独立GPU KDA10项、34层/272切片回归；实际全模型仍有上述数值边界 |
| mHC pre | **MATE** mate.hyperconnection.mhc_pre | 转换返回值顺序；传入4路残差、Sinkhorn20、两个epsilon、post倍率2；原始FP32 base/scale装载 | 实际权重独立公式对照及全模型推理；不把pre通过扩大为整个mHC/整模无误 |
| 普通RMSNorm | **MATE** mate.norm.rmsnorm | 展平Token维度，传入权重/epsilon，再恢复原shape | 参与当前模型GPU执行；不等同KDA的sigmoid-gated norm也已融合接入 |

MegaMoE的额外边界尤其要讲清楚：安装的MATE 0.2.8.post1中，
split-prefill确实支持activation_clamp；decode包装函数接收该参数却没有继续传给decode内核。
当前把小输入补到129行，padding路由ID为−1、权重为0，显式选用支持clamp的split-prefill实现，
仅返回真实行，前后同步/barrier保证IPC复用顺序。**已经接入FP8 MegaMoE，
但尚未接入一个经过本模型验证、且原生支持GLM clamp语义的高性能decode专用路径。**
这与此前“split-prefill不支持clamp”的错误判断不同，报告已明确更正。

## 5. 哪些已有GPU实现，但还没有换成MATE高性能实现

| 模块/能力 | 当前做法 | 为什么还差、后续需要什么 |
|---|---|---|
| KDA短卷积与状态拼接 | 我方Torch MUSA GPU展开、FP32乘加、SiLU，保留3步历史 | 需要匹配GLM q/k/v分片、卷积历史槽及读写语义的融合卷积接入与回归；不能仅因库里有同名卷积就直接替换 |
| KDA sigmoid-gated RMSNorm | 我方GPU FP32归一化、权重和sigmoid门控，转回BF16 | GLM使用sigmoid门，不应误用其他模型的SiLU门；需核对MATE可用接口及dtype/舍入顺序 |
| mHC post | 我方Torch GPU einsum与乘加 | 必须核对残差组合矩阵的方向、post门及输出舍入，再接融合实现；当前未证明现成MATE post接口在该配置下可直接等价替换 |
| DSA/NoPE MLA | 吸收式投影、paged latent读取、稀疏top-k掩码，Torch MUSA GPU attention；cache为BF16 | 原生FP8 sparse MLA需要接通cache量化尺度、分页布局、index/top-k契约、prefill/decode与PD交接，不能只换一个attention函数 |
| IndexPool/kPool与尾部状态 | 现有模型层/后端GPU实现 | 需对实际MATE索引器/池化接口做形状和状态契约核对；当前已有短前缀检查，长上下文分页/复用覆盖不足 |
| 非专家投影、前3层dense FFN、共享专家 | TorchMUSA BF16 GPU GEMM；共享专家TP8单独归约 | 本轮优先替换路由专家，未把全模型改成FP8；若做其他FP8或融合GEMM，需分别接布局、尺度和数值回归 |
| 张量并行归约 | MCCL；当前选FP32求和后转回BF16 | MCCL是通信库，不能笼统称为MATE算子。custom-allreduce未在本轮启用/验证 |
| P/D状态交接 | 现有xLLM native调度、传输及我方模型状态接口 | 它不是单一MATE算子。随机模型单机/双机一致与真实请求已验证；不能因此宣称所有长上下文/并发状态场景都通过 |
| Chat/推理解析与流式用量接口 | 单实例v4曾验证一次结构化工具调用；当前PD普通文本输出含思考分隔，流式请求include_usage=true却未返回usage | 这是服务协议集成边界，不是MATE数学算子；本轮按用户要求仅记录，测速以同request ID的native日志核对Token数。当前PD Tool Calling未单独验收，不能外推AutomationBench环境已完成 |
| Graph、MTP/投机、视觉、更广CP/DP | 当前未启用，部分配置入口主动拒绝 | graph要处理动态分页、主机控制与Gloo barrier、固定地址/shape及MATE捕获支持；MTP/视觉是独立能力接入与验证，不是普通逐Token文本推理必须先开启的数学环节 |

上述在线模型张量计算都在MUSA GPU上；CPU负责控制、tokenizer、权重读取和离线重排、
IPC元数据及barrier。**没有把专家或attention推理回退到CPU，也没有从零另写一整套底层FP8 MoE内核。**

“为什么还差”主要是接口、状态、布局和数值验证没有完成，并不能简单概括为“MATE没有这个算子”。
若MATE当前接口确实缺失GLM所需语义，应给同事提供最小形状、dtype、参数和对照结果；
协作问题清单已写入MATE协作问题与最小复现入口.md，尚未代用户发送给任何人。
