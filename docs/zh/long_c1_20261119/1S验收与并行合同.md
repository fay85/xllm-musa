# SGLang 本机 20k 参考：复验口径

此处“参考”指 SJ9→SJ10、8+8、GPU Engram 的本机变体。不是交付指南的 host Engram 或 C48。快报不能与 1+5 混均值。

|P 并行|8 个调度 rank 的标记 ATTN_CP<i> TP<i> EP<i>。server_info: TP8/EP8、attn_cp_size=8、dp_size=1、interleave。源码 parallel_state.py 中 CP 宽=TP 宽时复用全 TP 组；MUSA 上 EP=TP 同样复用。此配置下 attention TP 是 8 个单元素组|CP8×TP8×EP8 需要 512 卡|

逐条验收用 `tools/musa_deepseek_v41/audit_sglang_long_c1.py`，入参为一组 performance/input… 目录、Decode server.log、实际 --length 与 --count。单独启动前记录脚本/库；服务预热的 4-token 非流式 /generate 不计入用户暖机。计分包含全部预定流；慢请求照计。P tail 的“整批 graph: False”不与内部尾部图矛盾；日志中 tag.strict 的 fallback 是包版本标签选择，不是量化 kernel 回退。

首组 S20A（1+5，6 条独立 ID 全对上 D 终态，退出后 16 卡释放）：正式均值 TTFT 7613.303 ms、TPOT 16.326 ms、E2E 24.315 s、42.114 token/s；单条 E2E 22.954–26.775 s；计分 verify 293–303 轮，accepted 723–733、proposed 1465–1515。暖机与计分独立。这一时点仅为 F1，未给出跨框架结论。

S20B 也是全新 P/D/Router；每组另有 1 暖，不混算。12 个 SGLang 响应和 6 个 xLLM 响应均逐一对上各自 D 端 request ID、成功长度和零前缀缓存。SGLang 的 dp_rank/接受数量/正文并不要求跨请求相等；xLLM 控制五条计分均为 701/975。两套系统实际使用同一工作负载，并非同一种并行或投机算法。xLLM 日志证明两侧走 deepseek_v41 native C++ template、fast tokenizer；与实际构建提交 980d9da1 对应的单 user 无工具 chat 分支，按 BOS、User、正文、Assistant、</think> 构造，配合同词表 SHA 与服务端实际长度核对；xLLM 未提供逐条 token ID 回显，不伪称远端 tokenize 对账。

至此为**该本机变体 F2**，不推广至交付指南。X20K1 比此参考多用 32.456 s/E2E，约 12.624 s 在首字前，19.833 s 在之后。P rank0 有 79 个串行 chunk（78×256+32），各条首末层 host enqueue 区间累计 18.742–19.499 s，不是纯 GPU 计算时间。先用现有 512 合同检验减少分块是否真能改善 20k E2E，再评估长上下文 target 图和更大工程改动。不能只比较 TTFT。

独立 D trace（20000/32、不计入上表）：启用采集前/采集中/退出后的 E2E 分别为 20.757/37.011/21.201 s，首个正文约 19.306/19.335/19.970 s。采集明显扰动生成阶段。rank0 有 98780 个 kernel，两种 dtype 的 8-rank custom reduce 各出现 559 次；不能用 profiler 的聚合时长外推成无 profiler 收益，尤其不能跨卡相加。证据为 `00_control/X20K1/trace` 的 3 条流、SHA 清单及 `02_trace/X20K1/sj10` 的 8-rank trace/原生栈。没有在 20k P 上采集全量 Kineto，避免为 79 个 chunk 导出巨量事件；P 的 shape 与时长证据来自实际 rank0 段边界及独立 2k trace。
