# 20k：已缩小到哪些疑因

**没有新的跨框架 20k 比较。** 下列工作取证于 11/18 的成功与失败组；不把它们冒充 11/19 的新跑分。

## xLLM
在同一份服务日志和 EvalScope DB 里按请求 ID 对上后，2k 每请求 accepted/proposed=690/1008，20k 为 701/975。两个长度各自的 1 暖 5 测正文 hash 组内一致。2k→20k 时 TPOT 从 16.966 增至 36.078 ms/token，这两个固定文本的接受比例反而上升，不能用“长输入接受率下降”解释。

实际源码 980d9da1 的 `deepseek_v41_native.h` 和当前干净 worktree 的该文件相同：
- P 端启用 Engram 时入口限制单批至多 512 行，hash、gate 和 injection 也有限制。1024/2000 不能再当只改配置的扫描；要先建立带 lookback、历史环和尾块掩码的子批合同，不能删掉 CHECK 碰运气。
- target 仅在 `context_length <= 4096` 且行数/verify 条件满足时调用 `decode_graph_->run`，更长则走 `forward_with_capture(...,decode_capacity=0)`。这是 target 路径，不代表 draft 和所有子图全关。历史 20k Decode rank0 中 `layer begin index=0 q=4 kv>20000` 共 1950 次，与 6 个请求各 325 轮一致；归档尾部还有后来失败的 2k 请求，不能把那里的 4096 容量图算作 20k 命中。8k 的独立进程实测及 D 分段计时比直接放宽 Graph 上限更有价值。
- 每台 8 rank 各自为 world=8、DP1、CP1、EP8。路由专家 moe_tp_size=world/ep=1，每个 rank 单独持有其专家分片，EP 组覆盖 0…7，Attention TP 也是 0…7；`cp_group_` 在 CP 关闭时可别名 TP 句柄，日志中的 handle 大小不是 PCP 已启用。P 共享专家复制，D 共享专家 TP8。MUSA native 构造函数要求逻辑 cp_size=1。没有测得 CP 收益，不能用 CLI 启 PCP。

## SGLang
本机镜像 RepoDigest 后缀 `df97856006bf521c7174dfb007d3ef7e80398570214a0cf2ac66a9b70be92669`，image ID 后缀 `1612b9c34896d7efb631975bf49542693c4c6d129554c63f32a31b13edc37337`；与原 32k/C48 成绩的绑定未证实，不单独阻塞 C1。MATE 0.2.6、deep_ep 1.1.0+9017268.musa438.ringreset1、apache-tvm-ffi 0.1.12.dev1+g76a395be4.d20260928。未查到某个 distribution 名不等于运行时没有该组件。

首次段错那轮按 rank0 原日志：P 权重+DSPark 加载增量 66.26+1.37 GB、建池后可用 9.94 GB；D 为 67.29+1.47 GB、建池后 7.10 GB、启动完成 4.13 GB。这些不是执行峰值。P/D 最终 full=65536、c4=16384、c128=512；SWA 分别为 9728/2304。不能把 full 池按 DP8 再除一次，也不能直接拿 SWA 行数与 20k 比。P 实际 8 块为 4096、4096、1280、3840、1280、3840、1280、288；rank 标签是 CP_i/TP_i/EP_i，而 D 是 DP_i/TP_i/EP_i。区别调度 chunk、CP rank 局部行数和 ring/压缩池容量。

资源审计、容器内库映射与 hash 均须归属到对应运行；xLLM 实际映射不能代替 SGLang 映射。没有完整的 20000/1024 请求时仍是 F0；达到两次独立 1+5 前不算 F2。

## 11/19 新 2k 恢复门槛（不是历史 2k B 的重测成绩）
完全重建 P、D、Router，使用 20k 失败轮的最终配置先送入同一个 2000/1024 负载。服务端 tokenize 返回与冻结 IDs 一致；客户端 1+2 全部成功且 finish_reason=length，但**不能作为正常性能参考**：
- 两次计分平均 49.327 s；流出的正文从开头几个词即变为不连贯的多语符号，三个正文 hash 不同。历史 2k B 的 1+5 输出均是同一个连贯正文（哈希 1e32f5c8…），为 16.996 s。当前 P 实际只发单块 2000，cached=0；当前 D 的 DP0/1/2 接受率日志约 0.01–0.09，full graph 标记为 True。故障现象不必等 20k 才能观测。并非一次完整的模型精度验收，也不是根因已经定位。
- 真实 maps 已取，P/D 加载系统 libmusa.so.4.3.8，哈希 8eee0afc…；D 的 deep_ep_cpp 090e0fe2…、libtvm_ffi 4419d50f…。不能反推 11/18 失败进程的实际映射。
- 还原字节级启动身份：历史成功轮 D 脚本与归档最终 D 源脚本 SHA 一致（330dbafb…）。P 成功脚本的 SHA aff973ba…；精确重建后，对比最终脚本实际执行参数只差 allocator False/True、mem-fraction-static 0.90/0.89、chunk 32768/4096（还有命令换行，不改变 argv）。历史成功进程与本轮 JIT/传输状态仍可能有差异。新鲜双端 2k 的低接受率排除了“故障必需复用旧 D”这一条件，但没有证明与 20k 段错同根。
- SSE 响应 id 与 router 层 id 是不同命名空间，不能声称两者已按同一字符串对账；router HTTP200 也不等于最后一个 token 已结束。原始输入、服务端状态、流数据库和事件记录分开保存。
- 证据：`00_control/sg2k/{sglang/runtime,sglang/performance,sglang/configs}`。只在全新服务下测试单因素；首先只把 P allocator 恢复 False，不调 D、chunk、mem fraction 或 DSPark。

## 恢复结果与 20k 快报
P allocator 单改为 False 后，2k 三条流的哈希全部回到历史 1e32f5c8…；两条计分的 TTFT/TPOT/E2E 为 1265.920 ms / 15.584 ms / 17.208 s。它支持“该配置下分配模式会影响输出”而不能定位错误在分配器、注册还是其他地方。新进程启动状态也是未控制到字节级的变量，不应把一个方向的恢复当作驱动归责。

20k 新启 P、D、Router，实际 20000/1024，1 暖 1 快报（不是 F1/F2）：6381.283 ms / 15.996 ms / 22.745 s，45.020 输出 token/s。暖机 40.399 s 不计入正式。两条流 finish_reason=length，正文起始连贯、哈希不同。P 实际发出 4096+4096+1280+3840+1280+3840+1280+288=20000；每块有 tail graph LOOKUP。固定 SHA 中 LOOKUP 位于 miss 早退之后，该分支经首次 capture/refresh 或既有图 refresh，最终进入 replay。日志里的 P 整批 graph=False 不是 tail graph 被禁用。D 的长上下文行 graph=True，target verify/draft verify 的实际捕获分别为每请求 6/5 行。P rank0 启动报告可用 9.87 GB、D rank0 图捕获后 4.13 GB；不当作最坏临时峰值。详见 `00_control/sg20k_allocF`。后续 1+5 单独启用 Decode 的 level 0 JSON 请求终态日志（不记录输入或输出正文，不开 profiler），以逐条匹配 SSE id。
