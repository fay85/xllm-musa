独立诊断 RQD 在 SNQ 模型配置上仅开 lifecycle 记录，不计分。三条实际 2000/1024、length、零 prefix 命中、正文与 732/1470 均不变。由 SSE ID 唯一关联 D sequence_terminal，取其 x-request-id 匹配同机 router 的 global_request_id。每条 14 个 router 事件；coordinator 和 rank 独立 lifecycle 文件为空，不声称有这些角色的分段。见 `tools/musa_deepseek_v41/long_router_ingress.py`：只接受合法 stage_duration，拒绝丢失和多匹配；不拿异步 FIRST_TOKEN_FLUSH 当 EvalScope TTFT。两端已释放。

前两列为本机事件内携带的服务端阶段时长；末列是异步行首毫秒时间戳之差。基本定位：这批请求绝大多数前部时间在 **router 报告进入 Prefill 队列之前**，而不是全在模型或入队后派发扫描。不能把两个阶段之和从客户端成绩扣除。三条请求处理之后，wallet wait/granted 都累计为 3，无每次等待时长，不能认定约 190 ms 是 credit 或 250 ms 控制事件轮询。

据此在 SNQ 上另开非诊断对照 T1Q，只将 router 的 `scalable_control_tick_ms` 从 100 改 20；不改变 coordinator 的 100、event pull 250、dispatch 10、credit grant TTL 3000、公平/准入及端点。两侧 flags 实测，两个 trace 开关均关。T1Q 的分数另记，不把诊断值作快筛分数。

非计分继续区分 CPU 初始化与等待。实际 router 映射了 librust_tokenizers，含 NativeModelRuntimeContext::thread_tokenizer 和 FastTokenizer::clone 符号；**仅证明路径存在，不证明调用或耗时**。不改 perf 权限，不在计分窗口 attach；可在独立 2k/32 请求仅按本任务 router 的固定容器、命令、PID 和 start_ticks 记录 CPU ticks、rchar 和 tokenizer 文件描述符，有效事件只约束假设，不能单凭 CPU 高作函数归因。

## H1D：同一全新服务中配对慢、快请求

在 T1Q 配置上独立重启 P/D/router，开启 router lifecycle，未发预热模板或分词请求。五条冻结的实际 2000/1024 依次发送，全部 SSE 对上 D 唯一 length/零缓存终态，正文 SHA、732/1470 不变。**整组只用于定位，不作 EvalScope 比分。** 读的是本任务固定容器及 namespace 内的 31180 router PID；每次检查 start_ticks，记录请求头部 350 ms 的 CPU/IO、线程 ticks 与文件描述符。未改变系统 perf 权限。
