# 给家明的本轮汇报

家明，我继续基于 1103 的 [xiaopangDeepseeekV41Flash](https://github.com/fay85/xllm-musa/tree/xiaopangDeepseeekV41Flash) 推进，完成了原版 1017 在 sj9/sj10 的双机 1P1D 验证，以及共享 SwiGLU 和三项 mHC 原语的逐项接入、对照测速。P/D 各 8 卡，eager、并发 1；实际是 Attention TP8、路由专家 EP8/专家内 TP1，共享专家完整复制。源码提交在这个共同仓库的个人分支上，不提 MR。上一项 SwiGLU 提交是 [34815f6a](https://github.com/fay85/xllm-musa/commit/34815f6ac23de6c3145a3392b7649874a37d4f27)，本轮 mHC 代码和全部实验记录纳入本次提交，最终提交网址另存于本地及 NFS 的“最终提交与交付记录.md”。

这次不是另写一套 GPU 算子，而是复用你 V4 在 xLLM 里已有的 MUSA kernel：共享专家的 clamped SwiGLU，以及 mHC 的 post、pre-combine、metadata/Sinkhorn。我增加了 C++ 绑定、Python 后端选择与 V4.1 调用，保留 V4.1 跨子层传递 pre_mix 的顺序。它们在 GPU 上执行；模型主体仍是 Python forward。这解决了 V4 已有原语尚未接到 V4.1 上的问题，不能说 V4.1 的完整 Mega-mHC、FP4 专家路径也一起完成了。

每项接入均测了两组输入输出，每组 1 次暖机、5 次正式请求，用未修改的 EvalScope 1.14.1，并核对两端服务的真实 token 数。只接 D 侧 SwiGLU 时，TPOT 分别改善 0.73% 和 0.61%，回答文本与 reference 一致；post/pre 的单算子计时变快，但整模型没有获得增量收益。最后加入 metadata 后，相对 post+pre 配置，256/256、2048/256 的 TPOT 分别下降 3.55%、4.23%（负值表示变慢）。 三项 mHC 全开后的结果是：256/256：TTFT 6246.94 ms，TPOT 1061.41 ms/token，端到端 276.9067 s，输出吞吐 0.9245 token/s，QPS 0.003611；2048/256：TTFT 29224.05 ms，TPOT 1054.26 ms/token，端到端 298.0593 s，输出吞吐 0.8589 token/s，QPS 0.003355。E 与前置 D 的输出文本未在两组都保持完全一致，性能变化还可能伴随专家路由变化。

数值方面完成了实际 sj9 上 79 项原语/真实层参数检查，六层随机小模型的 prefill/decode 和四种配置对照也通过，两道基础题每个配置均通过。但全模型开放式回答在部分配置间发生变化，固定 token 前缀的进一步数值检查又遇到了服务接口问题，所以现在只能说接入与功能/性能实验完成，不能说完整精度已经验收。融合开关保留为显式选择，不改变源码的 reference 默认值，也没有声称已由 trace 证明加速原因。

下一步先修复固定前缀验证入口、查清这些数值差异；同时优先确认原版 FP4 group32 权重加 block32 激活的专家 GEMM 接口，再接 GPU 路由、专家分组/combine。随后做 CSA2 的 norm/RoPE/Indexer/稀疏 attention 和缓存复用，再补 Engram、CED 尾部 replay 与完整 mHC 融合，最后推进 Graph/MTP。C++ 路线先做同一 GPU 算子的局部调用对照，待两条路线算子与模型语义对齐后再比整模型；不把交付 INT4 group128 权重与原版 FP4 混在一张性能表里。
