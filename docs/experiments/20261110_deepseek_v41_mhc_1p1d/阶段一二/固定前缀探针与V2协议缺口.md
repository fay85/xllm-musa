# 固定前缀探针未完成：Completion 与 native V2 的协议缺口

本轮原语/真实参数/小模型数值回归已经通过，但不能将原版整模型的固定前缀 P/D 数值一致性写成已通过。

## 观察到的事实

A 在全部性能测试后发出一次 `/v1/completions` 请求：官方编码得到原始 token ID，`max_tokens=4`、`logprobs=5`、temperature=0、非流式。服务返回 HTTP 400：`Stale or mismatched V2 output identity`，没有得到可比较的 token/logprob。

B 的两道流式 Chat 基础题通过后，同一探针再次返回该错误。P 的 rank0 日志明确记录 `V2 output missing attempt_seq`；router 记录 `reason=MISSING_OUTPUT_ATTEMPT`。随后 256/256、2048/256 测速请求全部失败。使用同一请求体做独立 HTTP 诊断得到 HTTP 503，正文为系统过载或推理容量不足，约 15 秒返回。该轮没有有效性能数据，最终验收为 FAIL。

B 失败后的所有客户端都已退出，16 个模型 rank 及控制服务正常 TERM 退出码 0，没有强杀。证据归档后，用 `stage1_swiglu_d_v2` 在完全相同算子配置下重新启动，去掉已知不兼容的前缀探针。18:03 已确认 v2 的 256/256 暖机成功完成，实际计数为 256 输入、256 输出，随后开始五次正式请求。正常重启我方服务并去掉探针后已恢复，但这仍不是只改变单一因素的因果复现；协议失败的资源回收需要单独检查。

## 源码对应关系

基于当前 `34815f6a`：

- `xllm/core/framework/request/request_params.cpp:503` 的 ChatRequest 构造从 `correlation().attempt_seq()` 设置 `v2_attempt_seq`。
- 同文件 `RequestParams(const proto::CompletionRequest&, ...)` 从约第 136 行开始，没有对应的 correlation 传递。
- `xllm/proto/completion.proto` 的 CompletionRequest 当前字段至 `logprob_token_ids=43`，没有 Chat 使用的 correlation 字段。
- `xllm/core/runtime/xservice_client.cpp:754` 明确在有 service_request_id、没有 attempt_seq 时输出上述错误。

这些事实支持“当前 native V2 的 Completion 链路未完整接入请求身份关联”的判断。它不是 mHC 数值错误的证据。HTTP 503 是否由该失败请求留下的服务容量状态引起，还需要单独复现和检查状态回收，不能只凭时间顺序断定。

## 后续怎么补

1. 核对当前 xllm_service 与 engine 的 Completion RPC schema、correlation、attempt/output event identity 是否一致。
2. 在入口、参数、调度、P/D 交接、成功及错误输出各处完整传递身份；不要在缺失时硬填 0 来绕过校验。
3. 验证失败请求的配额、容量预留、lease 和 cache 资源确实释放，后续 Chat 请求仍可运行。
4. 单独做小模型协议回归：原始 token 输入、流式/非流式、logprobs、正常结束、拒绝、取消。
5. 协议通过后再跑原版 1017 的固定前缀 P/D token/logprob 比较。不能将此比较称为全量 hidden state 或全词表 logits 的逐层验收。

本轮不把这个跨服务协议改动混入已经冻结的 mHC 二进制；先保持可运行的 Chat 1P1D 测试路径。

## 进一步核对 Chat 替代路径（19:07）

`xllm/proto/chat.proto` 已定义 `token_ids`、`logprobs`、`top_logprobs` 和 correlation，响应也有 token ID。不过 `xllm/api_service/chat_service_impl.cpp` 只在 `has_routing()` 时采用原始 token IDs；否则仍根据 messages 编码。因而，直接在 HTTP Chat 请求里加一个 `token_ids` 字段，还不能证明送入模型的前缀就是该数组：还需核对前置 xllm_service 的分词/转发行为、routing 及实际 token 计数和 ID。

本轮没有在性能请求运行中试发这一新探针。可在独立协议验证中先检查请求转发，再决定走已有 Chat 接口，还是修复 Completion 链路。两条方法都不能省略输入 ID 一致性的证据。


## Chat 替代路径的实际控制实验（20:06）

C 的全部性能请求和日志验收结束后，才执行这个探针，未混入性能样本。HTTP Chat 请求的 `messages` 故意问 `7×8`，而 `token_ids` 是官方编码的 `1.3+2.9`（21 个输入 ID）。如果原始 ID 生效，模型应回答 4.2。

实际返回输入计数 **17 token**，文本为 `56## `（探针强制 4 token、ignore_eos，后缀不能当作普通回答格式），与 messages 的问题相符。说明当前入口没有把客户端提供的 21 个 ID 当作最终输入。此次还仅收到 3 条 logprob 项，而 usage 为 4 个输出 token；探针在输入计数检查处立即失败，没有把后面的数据作为数值对照。

结果为 `PROBE_FAILED`、数值比较条数 0。已有 Chat protobuf 字段不等于前置服务允许外部调用者绕过分词。后续应明确 raw-ID 接口的实际转发行为，并核对特殊 token/logprob 的完整性；可以修复 Completion 的 V2 correlation，或给 Chat 提供经过验证的 raw-ID 入口，不能直接假定参数生效。

P/D 全部 rank 及控制服务随后正常退出 0。D/E 使用相同服务协议，不再重复发送这个已证明不满足前提的探针。原始请求、逐行 SSE 与响应在 NFS `02_correctness/stage2_post_chat_prefix/`，随 `stage2_post` 完整实验归档。
