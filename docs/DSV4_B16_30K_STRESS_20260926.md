## 已实测：128/128物理B16失败

证据：`logs/b16_physical_probe_20260926/`，16个独立prompt/range，client concurrency16。
服务实际命令及manifest均确认B16；不是仅客户端16并发排队到B1。

日志明确：`bucket=112 actual_tokens=112 query_width=7 num_sequences=16`，进入Graph capture后：

```text
deepseek_v4_dsa_cache_ops.cu:2875
Check failed: sequence_index < block_table.size(0) (16 vs. 16)
```

8个rank均触发该检查（部分rank为17 vs16）。调用链是target verify → Graph capture →
Attention `build_indexer_topk` → `deepseek_v4_indexer_topk_impl`。

- 16请求全部stream中断，0请求完整完成；不是“0%模型数学准确率”，而是功能测试失败。
- 无有效TPOT/TGS或稳定TTFT，不能使用客户端首片段时间作为完成请求性能。
- 尚不能运行B16固定GSM8K100及2500/1500正式性能；100题输入已准备，未用小样本成功替代。
- 第一阻塞点不是OOM或GPU故障，而是明确的host CHECK序列映射错误。

源码证据：`DeepseekV4AttentionImpl::build_query_ranges`（attention.cpp约1261行）仅对
Graph KV只有一个sequence的compact verify返回整段q7。多sequence时进入Graph默认
`for token in total_tokens`路径，生成112个单token ranges；分页表仍按真实16请求生成。
因此seq_idx=16首次超过16行表。修复不能只放宽CHECK，必须保留16组q7的序列、KV、状态映射；
Graph key及C4/C128边界亦须覆盖所有sequence，而非仅第一条。此次测试未擅自修改这些模型逻辑。

## 30K单请求对照结果

为了区分prefix-cache边界与30K调度容量，另起B1服务做了两个不混用的对照：

1. B1、prefix cache关闭、`max_tokens_per_batch=10240`：scheduler拒绝单序列，日志为
   `Request prompt is too long, no enough memory to schedule a single sequence. prompt_tokens=30000, pool_blocks=6272`。
   没有进入模型计算，不能计作精度或吞吐结果。
2. B1、prefix cache关闭、把`max_tokens_per_batch`及prefill chunk改为32768：服务启动阶段
   在`kv_cache_estimation.cpp:417`失败：`kv_cache_cap->c4_count() > 0 (0 vs. 0)`。
   这是更大的临时prefill/workspace预算挤掉C4 KV容量，不能简单靠增大batch token上限解决。

因此当前30K/1K存在至少两层独立限制：prefix cache请求会在
`deepseek_v4_attention.cpp:2253`触发`cached_prefix_tokens=48, compress_ratio_=0`边界断言；
关闭prefix cache后又受单序列调度容量限制，增大batch预算还会导致C4 KV容量归零。
1600请求尚未完成语义生成，不能报告任何长压吞吐；已提交18个请求（16个首批、2个服务
退出后的连接失败），均无完整响应，全部保留在
`logs/b16_30k_probe_20260926/long1600_run/`，未重试替换。

## 本轮结论

- 真实物理B16 Graph+DSpark：**不通过**，首个16请求批次在Graph capture期间sequence-index越界；
  因服务退出，B16 GSM8K准确率及2500/1500性能均为“无有效结果”，不能写成0%或某个TPOT。
- 1600×30K/1K：**未跑通**，首批即暴露prefix-cache/compression边界；关闭prefix cache的B1
  对照又暴露调度/KV容量限制。它不是显卡故障、不是单纯OOM，亦不是成功完成1600请求。
- 已保存的合成长序列数据集可复用；修复后必须重新从全新服务运行1600请求，并分别记录
  HTTP错误、实际物理batch、prompt/completion usage、TTFT/TPOT、GPU显存和各rank错误。
